# Libitu Stage 2：原音获取、片段预处理与跟读分析——外部 AI 咨询材料

整理日期：2026-09-10。

本文可以单独上传或完整粘贴给其他 AI，无需访问项目代码或先前对话。它汇总目前的产品背景、讨论结论和待验证方案，不代表新增功能已经实现。

## 给评审 AI 的请求

我们正在设计一款英语跟读产品，请对以下方案做独立技术评估。当前最关心的是：**用户选中一个 YouTube 视频片段后，应用能否自动、稳定、低延迟地取得该片段原音，完成句子级预处理，并在用户录音后给出有依据的比较。**

请先评估原音获取，再评估分析和存储。不要默认我们已经拥有可下载的媒体文件，也不要把“有时间戳”当成“已经取得音频”。欢迎指出现方案的问题或提出更简单的替代方案。

请区分：技术上可做到、当前可稳定用于生产、依赖内容或平台授权、仍需实测验证。关于模型效果和等待时间，请说明依据，不要给出没有评测支持的准确率。

## 1. 产品背景与用户需求

产品名为 Libitu，是一款把真实英语内容转成学习与口语练习的 Web 应用，配有 Chrome 扩展。现阶段的重要入口是 YouTube 视频。

基本流程：

```text
选择 YouTube 视频
    → Stage 1：阅读字幕、理解内容、查看语言分析
    → 选择一个练习片段
    → Stage 2：逐句听原音、跟读录音、比较与反馈
    → 后续：练习历史、进步对比、能力估计与内容推荐
```

Stage 2 有三个分析层：

| 层 | 希望帮助用户学习什么 |
|---|---|
| Sound | 音素与连读、弱读、闪音、同化、省音等现象 |
| Rhythm | 停顿、语速、音节/词时长与重音节奏 |
| Melody | 相对音高、音域、语调走势与句子重音 |

用户的主要诉求：

- 播放、录音和回放按钮靠近视频，位于三层分析上方。
- 不希望每练一句就进行一次原音授权，也不希望手工获取或上传参考音频。
- 不希望为了准备原音，必须先把所有句子按 1× 播放一遍。
- 希望应用自己准备原音，切句、切层与反复练习顺畅。
- 录音后可以异步分析，但应立即能够回放，并继续练下一句。
- 后续需要跨设备历史、进步对比、用户能力估计和智能推荐。

暂定首发海外市场，具体国家与部署地区尚未确定；中国大陆部署与监管不属于当前首发范围。项目预算、预期并发和 GPU 资源尚未确定，不能默认已有大规模计算基础设施。

## 2. 目前已经实现的内容

| 范围 | 已实现 | 尚未实现或验证 |
|---|---|---|
| 句子与导航 | Stage 1/2 共享带版本的句子；目录、上一句/下一句、循环、倍速、刷新恢复 | 现有字幕推算时间不是精确词/音素边界 |
| 用户录音 | 浏览器 MediaRecorder，最长 60 秒，停止、回放、重录、删除 | 当前录音临时保存在页面内；尚无服务器录音历史 |
| 原音获取 | Chrome 扩展捕获包含 YouTube 播放器的 Libitu 标签页音频 | 尚无服务器文件获取、片段媒体资产管线 |
| 基础声学分析 | 浏览器 Web Worker；Silero V5 检测语音区间；Pitchy 4.1.0 测量基频与相对音高 | 真实多说话人、背景音乐、设备差异下的质量仍需评测 |
| Sound 提示 | CMUdict 发音词典和保守的确定性规则，显示条件性语音现象候选 | 没有经验证的真实连读/弱读/闪音等声学检测器 |
| 三层界面 | Sound/Rhythm/Melody 独立标签页，共享句子、录音与分析状态 | 不能因图形完整就认为词重音或语调评分已经完成 |

当前技术栈是 Next.js/React/TypeScript、FastAPI/Python、Clerk 身份验证、Supabase Postgres、Upstash Redis。已有文本任务与后台 worker，但尚未实现专门的文件媒体处理、对象存储上传和学习者声学任务系统。

当前 Rhythm 主要展示语音跨度与内部停顿；Melody 展示相对音高曲线和音域。这些是描述性测量，不能直接代表发音总分、词级语调正确性或 CEFR 等级。

## 3. 为什么重新讨论原音方案

### 当前 Chrome 方案的工作方式

YouTube 官方 iframe 用于视频播放和定位。当前程序通过 Chrome `tabCapture` 与 offscreen document 捕获 Libitu 标签页正在播放的声音，再转为音频数据进行本地分析。

它获取的是标签页声音，不是通过官方接口得到干净的原始音频文件，因此也可能录入背景音乐、广告或标签页中的其他播放声音。

现有流程已经从“逐句授权”改为“一次练习会话共享采集连接”：

1. 网页点击 Enable practice audio。
2. 用户在当前 Libitu 标签页显式点击扩展工具栏。
3. 后续句子在正常播放时自动采集，复用连接与有限缓存。

Chrome 的扩展调用授权与麦克风授权是两件不同的事。网页上的普通按钮不能直接代替扩展调用授权；从 YouTube 标签页打开 Libitu，也不能假设授权自动转移到新标签页。

当前采集要求 1× 连续播放，是应用为了时序测量可靠性设置的条件，不是 Chrome 规定所有录音必须 1×。当前 30 分钟会话上限、切换片段/退出时关闭等，也包含应用自身的实现选择。

这个方案即使不再逐句授权，仍有首次操作、实时播放等待、会话中断、扩展与浏览器兼容等体验成本。因此我们希望改变默认原音获取架构。

## 4. 讨论结论：哪些已确定，哪些只是提案

### 已确定的方向

- **以文件式原音预处理作为目标架构。** 分析可解码的媒体文件或片段字节，不以用户实时播放并录制标签页作为正常主流程。
- 原音准备尽量由应用完成，学习者不承担逐句授权或手工上传参考音频的工作。
- 可以在服务器处理和保存用户录音及学习结果，不再坚持所有数据只能在浏览器。
- 参考媒体和用户录音分开管理；可以共享的参考资产按内容保存，用户练习引用它，而非为每个人重复存一份原音。
- **LLM 做文字/音素层面的规则推断，不做声学分析。** “规则上可能发生”与“原音实际发生”“用户实际读出”必须分开。
- 文件获取成功不代表语音现象检测成功，缺少证据时不能生成假评分。

### 最近提出、希望重点评估的默认流程

**用户选中练习片段后，再按需获取和处理该片段；不默认下载整条视频。**

例如一条 20 分钟视频，只练 02:10–02:55 的 45 秒：先尝试获取该范围及少量边界上下文，再在服务器切句、计算特征。以后选择另一个片段，再准备那个范围。

当前句优先，片段内下一两句预取；允许部分准备好就开始练，不等待全部高级分析完成。热门授权内容可提前处理，但不是所有内容默认全片入库。

### 还不是最终决策的建议

- 私有对象存储优先沿用 Supabase。
- 第一版迁移现有 Silero/Pitchy，再用评测决定是否换 CREPE 等模型。
- Python 编排/解码配合 Node 原生声学 worker，以复用现有 TypeScript 计算；也希望比较全 Python 的简化方案。
- 没有可用文件时保留官方播放器、文本与基础录音，提示无法进行完整原音对比。
- 内容方文件作为完整体验的首批来源是建议，尚未确认真实供应方；不能据此把 YouTube 用户入口悄悄改成上传文件才能用。

## 5. 原音获取：最重要的未解决问题

“只保存一个片段”“只分析一个片段”“网络上只下载一个片段”是不同的能力。

| 来源情况 | 目前考虑的办法 | 需要验证的地方 |
|---|---|---|
| 内容方交付文件或允许裁剪的 API | 系统获取目标片段 | 实际来源、许可、时间映射和费用 |
| 可合法访问的 HLS/DASH 分段媒体 | 获取覆盖该时间的分段，再裁剪 | 多取多少相邻数据、音轨和边界是否正确 |
| 可定位且支持 HTTP Range 的文件 | 按索引读取相关字节 | 容器、索引、服务器能力和实际传输量 |
| 仅支持完整文件下载 | 下载全文件后切片 | 不满足默认的局部下载目标，成本可能过高 |
| 已在我们存储中的授权媒体 | 直接读取所选部分 | 无需重新从外部获取，但仍有内部读取与计算成本 |
| 任意普通 YouTube 链接 | 尚无已经验证的默认生产路径 | 可获得性、授权、失效处理和稳定性 |

讨论过 `yt-dlp` + FFmpeg，包括 `--download-sections` 时间范围功能。它是技术候选，不是已经部署的接入方案。指定起止时间不等于证明实际只传输了这几秒的数据，需要测量下载字节数与服务器请求行为。

当前也没有证据证明“任意 YouTube 链接都能长期稳定地从服务器获得对应音频”。请评估真实部署下的限制，而不只给出一条本机命令能跑通的例子。

内容方许可与平台许可需要分别考虑。普通 YouTube 官方播放能力不能自动推导出可以下载、分离音频、长期保存或共享衍生资产；本地采集和仅截短片段也不自动解决这些问题。我们希望得到具体可行的接入路径及边界，而非笼统断言“完全没问题”或“全部不可做”。

## 6. 当前候选处理链

最初讨论过：

```text
Whisper → MFA → DeepSeek 标注 → CREPE + Silero → JSON 入库
```

现在不打算把这个顺序当成固定串行链。原音准备和用户比较分别执行，文本规则也不必阻塞基础声学计算。

### 参考侧：每个内容/片段版本处理一次

```text
检查音源能力与缓存
    → 用户确认片段
    → 获取有权处理的片段音频
    → FFmpeg 解码，核对音轨与源时间偏移
    → 核对字幕与实际说出的内容；必要时 ASR
    → 句子时间校验与切片
    → 基础语音/停顿/音高特征
    → 词与音素精细对齐、已验证的现象检测（后续能力）
    → 保存版本化音频、特征及每层就绪状态
```

ASR 是按需环节：缺少或不可靠的逐字稿需要识别；已有可信且与文件绑定的逐字稿，不一定需要重复跑 Whisper。Whisper/faster-whisper 是候选，不是既定唯一选择。

MFA 等强制对齐器是在给定文本条件下寻找时间边界，不独立证明字幕正确。清理后的阅读文本可能删除重复词、语气词或改变数字写法，需要保存“显示文本—实际语音文本—时间”的映射。

### 用户侧：每次录音后异步处理

```text
浏览器录音 → 停止后立即可本地回放
    → 已选择云端分析的用户上传私有录音
    → 检查音质与是否说了对应内容
    → 独立分析、必要时对齐
    → 与固定版本的参考数据比较
    → 推送结果，保存本次练习与历史
```

必须处理漏词、加词、重复、读错句子和速度差异，不能仅把目标文本强行对齐到任意录音就开始打分。

当前候选基础算法是 Silero V5 + Pitchy。CREPE/torchcrepe、其他 ASR/对齐/发音评测技术可以提出替代，但请说明改善什么、增加什么成本，以及怎样验证。

### 对三层证据的要求

| 信息 | 允许如何使用 | 不应如何使用 |
|---|---|---|
| 词典与文本规则候选 | 解释可能的发音方式及条件 | 直接当成原音或用户已实现的现象 |
| VAD 与停顿测量 | 显示可测的语音时序 | 单独判定词重音或连读正确 |
| 相对音高曲线 | 展示音域与走势差异 | 只按相同时间比例匹配就给发音总分 |
| 强制对齐 | 提供待核验的词/音素位置 | 把对齐成功当成内容正确或发音准确 |

最初有“规则推断接近确定性、可能达到 95% 以上准确率”的假设，目前没有支持它的评测。诸如“两元音之间的 /t/ 必然闪音”或“功能词非句首就必然弱读”不能直接写成已验证规则，还涉及重音、音节结构、语境、方言和实际说话方式。请评审规则覆盖和声学检测时分别讨论。

## 7. 顺畅交互需要什么

- 页面进入、切句和预取都不自动播放或打开麦克风。
- 参考音频已准备好时直接播放；新片段显示真实阶段，当前句先就绪先可用。
- 不因 Sound 的高级检测尚未完成而锁住 Rhythm、Melody、录音或回放。
- 原音、视频与用户回放避免同时发声；录音时暂停其他播放。
- 文件原音与 YouTube 视频如何呈现尚需评估。目前建议句子音频播放时暂停 iframe，保留“看原片”入口；不声称已解决外部音频与 iframe 的精确同步。
- 正常原音流程不依赖 Chrome 采集授权。麦克风仍需浏览器权限，产品不能保证所有环境永久只问一次。
- 当前“切句即清除本地录音”需迁移为有界的 attempt 管理；迟到结果属于原句，不能覆盖新句。
- 上传完成的分析可继续运行；未上传录音跨刷新恢复尚未实现，也未承诺。

缓存以源版本、音轨、共享句子、时间范围和分析版本为依据；换源、改字幕或更新算法不能误用旧结果。对于同一许可范围内可共享的内容，应减少重叠片段的重复获取和计算。

## 8. 服务端存储与后续用户数据

以前的“原音和用户录音都不上传服务器”限制已经重新评估：用户录音、学习结果和历史允许进入服务器，但参考音频必须有相应处理与保存依据。

计划分开保存：

| 数据 | 保存方式与用途 |
|---|---|
| 参考片段与句子音频 | 内容级资产，在允许共享的权限范围内复用 |
| 参考特征与对齐 | 固定来源、文本和模型版本，可供多个 attempt 引用 |
| 用户录音 | 私有对象，仅属于对应用户 |
| 练习与评估记录 | 记录句子/参考版本、测量、质量、时间、倍速、看稿条件与模型版本 |
| 用户画像与推荐输入 | 后续基于多次练习等证据形成，不从单次音高直接推出能力等级 |

当前分析、长期录音回放、模型训练/人工复核是不同目的；训练与人工复核默认关闭、单独选择。需要保留期、录音删除、历史删除、导出和账号删除能力。

已有方案提出私有对象存储、短效签名、后端验证 Clerk 身份、持久任务表和 Redis 调度。媒体任务需要幂等、重试与崩溃恢复，参考处理和用户录音分析应隔离资源，避免长任务堵住即时反馈。

10 分钟下载签名、临时输入 24 小时清理、主动开启的录音回放保留 90 天等，均只是工程建议值，不是最终保留政策。不得把这些数字当成用户已经同意的条件。

## 9. 实施候选顺序与性能假设

| 阶段 | 拟交付内容 |
|---|---|
| F1 | 确认可用音源；验证范围获取、真实传输量、时间映射、服务端基础算法与耗时 |
| F2 | 片段/句子资产、对象存储、持久任务、基础质量检查和失败恢复 |
| F3 | 前端文件播放、预取、分层就绪、去掉正常原音采集授权与优化按钮交互 |
| F4 | 用户录音上传、异步比较、跨句任务、私有历史和删除 |
| F5 | 词/音素精细对齐、逐项验证的 Sound 检测与更深入的 Rhythm/Melody |

句子级原音内容与边界正确性不能推迟到 F5。需要高级证据的评分，在检测与校准完成前保持未评估。

提出过的性能目标包括：暖缓存下当前句数据约 500 ms 内可用、点击到首个声音约 1 秒内，以及暖 worker 对 10 秒用户录音从停止到基础结果 p95 不超过 8 秒。**这些没有经过生产基准验证。** 首次片段准备时间尚无可靠估计。

希望评估首段等待、下载流量、计算成本、模型加载、队列拥堵和前端缓存；请分别给出假设，不要把服务器推理耗时等同于用户端总等待。

## 10. 请重点回答的问题

1. **获取路径**：针对普通 YouTube 用户入口，最现实的原音接入方式是什么？官方接口、合作文件、服务器下载或其他方案各能覆盖什么场景？哪些需要外部授权或业务合作？
2. **按片段获取**：选定 45 秒后再获取，是否能减少真实网络传输？不同媒体格式和上游能力如何判断？怎样测出“表面切片、实际全量下载”？
3. **用户体验**：下载与预处理应该在片段选择的哪个时刻触发？冷缓存时怎样减少等待，又不对每条视频提前下载？哪些操作可以并行？
4. **播放体验**：如果视频仍用 YouTube iframe，句子文件如何与“看视频、听原音、跟读、回放”配合？是否有比两个播放器互斥更好的可实现方案？
5. **最小分析链**：已有字幕时，哪些内容需要 ASR、对齐、VAD、F0？哪些可以先省略？Whisper、MFA、Silero、Pitchy/CREPE 各自是否适合？
6. **Sound 检测**：连读、弱读、闪音、同化、省音分别能用什么技术识别？哪些已有可用工具，哪些要训练或标注数据，哪些不应作为第一版自动评分？
7. **用户侧比较**：如何处理不同声线、语速、口音、漏词、重复和错误文本？如何区分模仿程度、自然可接受变体和影响理解的错误？
8. **运行架构**：复用现有 TypeScript 算法的 Node worker，还是改为统一 Python 音频管线更合适？第一版是否需要 GPU、外部语音 API 或新增凭据？
9. **资产与历史**：重叠片段怎样去重和复用？参考更新怎样保留历史可解释性？用户删除录音后哪些记录可继续保留、需要什么依据？
10. **落地验证**：现方案哪些假设最可能失败？请给出一个最小验证实验，包括音源、样本、真实传输量、正确性和延迟指标，以及通过/停止条件。

其中第 1、2、3、10 项优先。最大的未决点是：如果用户期待任意 YouTube 链接都有完整原音分析，而实际音源接入只能支持有限内容，产品承诺应如何调整？请直接评估这个矛盾，不要默认它已经被解决。

## 11. 希望评审输出的形式

请按下面结构给出结论，不必先写完整业务代码：

1. 明确的推荐方案与成立前提。
2. 对现有假设的判断：成立、部分成立、证据不足或不成立。
3. 主要获取路径的对照表，分别说明覆盖、等待、成本、授权依赖与维护风险。
4. 从用户选片段到参考就绪、再到录音反馈的具体流程。
5. 第一版必做与可以推迟的分析能力。
6. 一个可执行的最小实验，以及必须补充的少量业务信息。

如涉及现行平台政策、API 功能或模型效果，请给官方文档/原始论文链接和核验日期。估算要说明网络、硬件、音频长度与并发假设。
