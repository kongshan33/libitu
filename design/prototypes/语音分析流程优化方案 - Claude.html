结论：目前没有现成的模型能直接输出“这里发生了同化”或“这里是连读”这样的标签。 学术界有相关研究，但没有成熟、开箱即用的工具。能做的是组合几种技术，其中最实用的是第 2 种。

1. 现成的东西能给你什么

工具/数据能提供局限
Allosaurus（通用音素识别）输出更细的音位变体，不局限于规范音素准确率一般，英语上比专用模型差，噪声大
Buckeye 语料库（约 40 小时自然口语）人工标注的实际发音，包含省音、弱化、flap 等是数据，不是模型；需要许可，也需要自己训练
TIMIT有 flap、喉塞音、闭塞段标注朗读语料，现象少，同化基本没有
Azure / SpeechSuper / ELSA 等发音评测 API音素级准确度、韵律分数给的是分数，不是现象标签，也不可解释
音频大模型（Gemini 等）能口头描述“这里有连读”不稳定，会编造，不适合当数据来源

2. 最可行的技术：带发音变体的强制对齐

这是真正能得到“实际发生了哪种发音”的方法，而且你已经在用 MFA：

  1. 在词典里为同一个词写多个变体，例如 that 在 that person 里有 /ðæt/ 和 /ðæp/，got to 有完整读法和 /gɑɾə/ 读法。
  2. 让对齐器在每个位置选似然最高的变体。
  3. 选中哪个变体，就是“发生了什么”的证据，而且有置信度（比较各变体的似然差）。

MFA 支持变体词典。变体可以由规则自动生成，不需要手写。这个思路对 flap、弱读、省音、同化都适用，也可以放在 Reference 侧离线跑一次并缓存。

3. 各现象的具体做法

连读（linking）：规则加声学确认。

  • 先从文本里找候选：前词以辅音结尾，后词以元音开头。
  • 再用词边界确认：词间间隙接近 0，没有喉塞音或能量断点，后词元音起始处没有新的重音爆发。
  • 这个比同化可靠得多，基本属于 Tier 1。

同化（assimilation）：规则找候选，再用变体对齐或声学验证。

  • 候选规则：词尾 t/d/n 后接双唇或软腭辅音。
  • 验证：变体对齐选中同化变体；或者看鼻音/塞音的发音部位线索（F2 过渡、闭塞段特征）。
  • 同化本身是渐变的，语言学家之间也会有分歧，所以我建议保持 Tier 3：只做 Reference 侧标注，不对用户评分。

其他现象（flap、弱读等）：沿用我上一条回复里的做法，用 Parselmouth 测时长、共振峰、能量，再配合变体对齐确认。

4. 如果想“批量得到这类数据”

分两条路：

  • 从文本生成预期：用规则或 LLM 对文本做连读、同化、弱读的预测，这本质上是一个文本到发音变体的任务，不需要音频。再用第 2 条的变体对齐去验证音频里是否真的发生。这样得到的标注是“预测 + 声学验证”，可信度比单用 LLM 高很多。
  • 训练自己的识别器：用 Buckeye 等语料微调 wav2vec2，输出实际音素。这是工程量最大的一条，我建议等前面的方案跑通、确认哪些现象值得做之后再考虑。

我的建议

对 ToneFlow，先做“规则生成候选 + 变体对齐验证”，只在 Reference 侧展示，用户侧只比较稳定的现象（连读、停顿、弱读时长、F0）。同化和省音先作为学习提示，不参与打分。这样既能得到可用的数据，也避免因为误判而误导学习者。

  • 核心流水线是对的：对齐得到表层音素，再和词典的底层音素逐位置比较，差异点就是候选现象。这就是我说的“带发音变体的强制对齐”。

  • 路线 B（SSL 隐层加 probe）作为科研方向描述得准确，但需要自己标注数据，不适合现阶段。

需要打问号的部分

  1. “新版 MFA 底层已经支持 wav2vec2 作为声学模型后端”：据我所知这不成立，MFA 的声学模型仍是 Kaldi 系（GMM-HMM 等），我没见过 wav2vec2 后端。这句很可能是编的，用之前请查官方文档确认。
  2. 自相矛盾的地方：它在坑点 1 里说 ASR/CTC 会掩盖表层发音，却在备选工具里推荐“HuBERT/WavLM 微调的音素 CTC 模型直接预测表层音素”。这类模型的训练标签通常是由词典转出来的规范音素，学到的也是规范音素，同样会掩盖。除非用 Buckeye 这类人工标注了实际发音的数据来微调。
  3. “MFA 选出最匹配的变体”说得太轻松：对齐器只能在你提供的候选变体里选，而且 n→m 这类差异的声学证据很弱（几十毫秒的过渡段），变体之间似然差往往很小。所以必须看置信度，差距小的不要下结论。
  4. FAVE-align 是较老的社会语言学对齐工具（基于 HTK），并不是专门用来自动标注连读和同化的，生态也基本停滞，不建议选。
  5. “工业发音评测大多是这套方案”：夸大了。工业评测主要用 GOP 或 ASR 置信度打音素分，很少去检测同化。
  6. “LibriSpeech + 人工音系标注”：LibriSpeech 本身没有这类标注。有实际发音标注的口语语料应该是 Buckeye（TIMIT 是朗读语料，现象较少），文档漏掉了最相关的数据集。
  7. 没有考虑你的场景：全程没有涉及延迟、用户侧还是 Reference 侧，也没有说明哪些现象值得做。

对 ToneFlow 的取舍

  • 采纳：第三节的流水线，只用在 Reference 侧、离线跑一次并缓存。
  • 不采纳：probe、FAVE、wav2vec2 后端这些说法。
  • 用户侧仍然只比较稳定的现象（连读、停顿、弱读时长、F0），同化和省音只作为学习提示。

结尾它提议的 MFA 规则 YAML 示例是有用的，可以要，但要对照你所用 MFA 版本的文档核对语法，因为规则功能是在 3.x 之后才有的。HuBERT probe 的代码现阶段可以不要。

方案：Reference 预处理 + 用户侧轻量并行 + 渐进返回

核心思路：把慢的活全挪到用户看不见的时间里，用户等待的路径上只留快的活。

一、流程图

二、各环节怎么做

阶段 0：Reference 预处理

  • 时机：Stage 1 → Stage 2 的段落选择完成后就在后台启动，用户进入 Shadow 页面时已经就绪。
  • MFA 整段一次对齐，用 json3 词窗口约束，固定开销只付一次。词典里为功能词和易变词配变体（弱读、flap、省音、同化候选）。
  • 现象标注方式：先用规则找候选位置，再用“选中了哪个变体”加 Parselmouth 的时长、共振峰验证，输出带置信度的标签。
  • 缓存键用 video_id + 段落哈希，按用户缓存。跨用户共享要先确认音频来源合规。

阶段 1：客户端

  • 录完立刻在本地算停顿、F0、能量，直接出 Rhythm 和 Melody 的预览曲线，用户几乎不用等。
  • 预览只作为即时反馈，最终结果以服务端为准。

阶段 2：服务端

  • 匹配判断不再用 Whisper 做主路径：把 Reference 文本强制对齐到用户录音（wav2vec2 CTC，CPU 上通常 1 秒左右），用逐词置信度当匹配率。这样 Whisper 不会替用户“纠错”，档位更准。
  • Whisper 只在低于 60% 档才调用，用来生成“你实际说了什么”的 diff。
  • CTC 对齐和 Parselmouth 提取并行，不再串行等匹配结果。
  • 比较环节不再用 MFA，直接用 Reference 包里的特征和 take 的特征比。

三、哪些现象给用户打分

层现象对用户方法
Rhythm停顿、重音、词时长比例打分词边界 + 相对时长、能量
Melody语调轮廓打分F0 转半音并按说话人归一化，逐词窗口 DTW
Sound连读、弱读时长、flap 时长、元音长度打分词窗口内 Parselmouth 比较
SoundH-dropping、末尾浊化提示，不重扣分声学特征，置信度低时不判
Sound同化、省音、喉塞音、drop-D仅 Reference 展示变体对齐，不对用户评分

四、关键工程细节

  • Worker 常驻：模型启动时加载一次，不要每个任务重新加载。
  • 队列：用 Postgres LISTEN/NOTIFY 或 Redis，替代轮询。
  • 渐进推送：用 SSE 或 WebSocket，检查点依次返回。你现在已经在保存检查点，改动主要在推送。
  • Reference 没就绪时：用户仍可录音，页面先显示匹配结果和本地预览，Reference 比较在就绪后补上。
  • 置信度阈值要标定：60% 和 85% 是原来“词匹配率”的阈值，换成对齐置信度后分布会变。先收集几十条真实 take，人工判断“读对/读偏/读错”，再调阈值。

五、预期收益

这些是设计目标，需要实测验证，不是已测数据：

指标现在目标
用户等待 MFA长，且每句重复基本为 0，已前置
首个结果出现要等全部完成本地预览约 0 秒，匹配检查点约 1 到 2 秒
完整结果不确定几秒内
匹配判断Whisper 可能替用户纠错基于对齐置信度，更贴近真实发音

六、实施顺序，按收益和成本排

  1. Reference 改成按段批处理并前置：改动小，直接消除最大的等待。
  2. 用户侧改为 CTC 强制对齐，Whisper 降级为兜底，并行 Parselmouth：改善效果和速度。
  3. 渐进推送加客户端本地预览：体感提升最明显。
  4. 变体词典和现象标注：先做连读、flap、弱读，再逐步加。
  5. （可选）音素识别器做 Reference 与 take 的对比：等前面稳定后再考虑，不要一开始就做。

七、风险与后备

  • CTC 对齐对口音或噪声敏感：置信度偏低时先标记为“不确定”，不要直接判错，必要时让用户用“我读对了”覆盖。
  • MFA 变体对齐在重度连读时可能漂移：Reference 侧的标签要带置信度，低的不展示。
  • 服务器没有 GPU 时：CTC 对齐和 faster-whisper（small 或 base）在 CPU 上可用，但要实测延迟再定模型大小。
